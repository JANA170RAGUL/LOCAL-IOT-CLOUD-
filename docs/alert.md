# Alert Engine Module

> **Version:** 1.0  
> **Status:** ✅ Complete  
> **Last updated:** 2026-07-12

---

## Purpose

The Alert Engine module records and manages security and telemetry events generated by the platform. While the Rule Engine *decides* whether a condition is met, the Alert Engine *persists* the resulting incident, tracking its lifecycle from creation, through operator acknowledgment, to final resolution and closure.

---

## Architecture

```
Rule Engine evaluates TRUE
    │
    ▼
ActionDispatcher (dispatcher.py)
    │
    ├── 1. Instantiates Alert Model
    ├── 2. Commits Alert to SQL (status = "OPEN")
    ├── 3. Retrieves generated alert_id
    └── 4. Publishes event on Redis pub/sub (with alert_id)
            │
            ▼
     Notification Engine / Operator Dashboard / WebSockets
```

Operators manage the alerts using specific workflow routes (`/acknowledge`, `/resolve`) that modify the state flags and update the timestamps in MySQL.

Inherits `id`, `created_at`, `updated_at` from `BaseModel`.

| Column | Type | Constraints | Default | Notes |

## API Endpoints

### `POST /projects/{project_id}/alerts`
Manually create an alert (for operator-generated incidents).

### `GET /projects/{project_id}/alerts`
List paginated alerts scoped to a project.
- **Filters:** `status`, `severity`, `acknowledged`, `resolved`, `search` (matches title/message).
- **Pagination:** `page` (default 1), `page_size` (default 20, max 100).

### `GET /alerts/{alert_id}`
Fetch single alert detail.

### `PATCH /alerts/{alert_id}`
Partially update fields.

### `POST /alerts/{alert_id}/acknowledge`
Acknowledge an alert.
- **Body:** `{"acknowledged_by": "operator_username"}`
- **Effect:** Sets `acknowledged=True`, `acknowledged_at=now()`, updates `status="ACKNOWLEDGED"` (if status was `OPEN`).

### `POST /alerts/{alert_id}/resolve`
Resolve an alert.
- **Effect:** Sets `resolved=True`, `resolved_at=now()`, updates `status="RESOLVED"`.

### `DELETE /alerts/{alert_id}`
Soft-deactivates the alert, setting `is_active=False` and `status="CLOSED"`.

## Business Rules

1. **Scoping:** When querying project alerts, the repository performs outer joins on `Rule`, `Sensor`, `Device`, and `Gateway` to resolve the parent Project. An alert belongs to the project if its triggering rule or parent sensor resides in that project.
2. **Workflow Progression:**
   - **Triggered:** `status = OPEN`, `acknowledged = False`, `resolved = False`.
   - **Acknowledged:** `status = ACKNOWLEDGED`, `acknowledged = True`, `acknowledged_by` set.
   - **Resolved:** `status = RESOLVED`, `resolved = True`, `resolved_at` set.
   - **Deleted:** `status = CLOSED`, `is_active = False`.
